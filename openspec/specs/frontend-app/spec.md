## Requirements
### Requirement: Vite single-page app runs locally with npm
The repository SHALL contain a Vite + React + TypeScript single-page app in `frontend/`, using React Router for navigation, Tailwind CSS and shadcn/ui components. From `frontend/`:
- `npm install` SHALL install its dependencies.
- `npm run dev` SHALL serve it at `http://localhost:5173`.
- `npm run build` SHALL produce static files in `frontend/dist/` that need no server-side runtime.

#### Scenario: Start the frontend
- **WHEN** a developer runs `npm install` and then `npm run dev` in `frontend/`
- **THEN** the app is served at `http://localhost:5173`

#### Scenario: Checks pass
- **WHEN** a developer runs `npm run typecheck`, `npm run lint` and `npm run build` in `frontend/`
- **THEN** all complete without errors

#### Scenario: Deep links work
- **WHEN** the built app is served and a browser opens `/account` directly
- **THEN** the SPA loads and handles the route instead of a server `404`

### Requirement: Backend URL configuration
The frontend SHALL read the backend's base URL from `VITE_API_URL` at build time (default `http://localhost:8000` in `frontend/.env.example`), and SHALL send every API request to that origin. `frontend/.env` SHALL be git-ignored.

#### Scenario: Requests go to the configured backend
- **WHEN** the app runs with `VITE_API_URL=http://localhost:8000` and a user signs in
- **THEN** the browser sends `POST http://localhost:8000/api/auth/login`

### Requirement: Generated API client
The frontend SHALL use TypeScript types and request functions generated by `@hey-api/openapi-ts` from the committed `openapi/openapi.json`, and SHALL NOT hand-write request or response types for API endpoints.
- `npm run api:generate` SHALL regenerate the client into `frontend/src/api/`, and the generated files SHALL be committed.
- `npm run api:check` SHALL exit non-zero when the committed client differs from what the current `openapi/openapi.json` generates.

#### Scenario: Client matches the spec
- **WHEN** `openapi/openapi.json` is unchanged and `npm run api:check` runs
- **THEN** it exits `0`

#### Scenario: Spec change is caught
- **WHEN** the backend adds a field to `User`, `openapi/openapi.json` is regenerated, and `npm run api:check` runs before `npm run api:generate`
- **THEN** it exits non-zero

#### Scenario: Types follow the backend
- **WHEN** frontend code reads a field that the `User` schema doesn't define
- **THEN** `npm run typecheck` fails

### Requirement: Bearer token in localStorage
After a successful login or registration, the frontend SHALL store the session token in `localStorage` under the key `token`. It SHALL send it as `Authorization: Bearer <token>` on every request to a protected endpoint, and SHALL NOT use cookies for authentication. After a password change it SHALL replace the stored token with the one returned. On sign-out and account deletion it SHALL remove the token. Whenever an API response is `401`, the frontend SHALL remove the token and show `/login` with `next` set to the current path.

#### Scenario: Token sent on protected calls
- **WHEN** a signed-in user opens `/account`
- **THEN** the request for the current user carries `Authorization: Bearer <stored token>` and no cookie

#### Scenario: Survives a reload
- **WHEN** a signed-in user reloads the page
- **THEN** they are still signed in

#### Scenario: Revoked token
- **WHEN** the stored token has been revoked elsewhere (e.g. by changing the password on another device) and the user opens `/`
- **THEN** the token is removed from `localStorage` and the login page is shown

### Requirement: Content-Security-Policy in production
Production builds SHALL include a Content-Security-Policy as a `<meta>` tag in `index.html`, generated at build time, that:
- allows scripts, styles, fonts and images only from the app's own origin
- allows `connect-src` only to its own origin and `VITE_API_URL`
- forbids inline scripts, `eval` and objects

The production hosting configuration SHALL also send `Content-Security-Policy: frame-ancestors 'none'` as a response header, since a `<meta>` policy can't forbid framing. The dev server SHALL NOT enforce the policy, because Vite's hot reload needs inline scripts. Application code SHALL NOT use `dangerouslySetInnerHTML`.

#### Scenario: Injected script is blocked
- **WHEN** a production build is served and a script from another origin or an inline `<script>` is added to the page
- **THEN** the browser refuses to run it

#### Scenario: API calls are allowed
- **WHEN** a production build is served with `VITE_API_URL` set to the backend's origin
- **THEN** requests to the backend are not blocked by the policy
