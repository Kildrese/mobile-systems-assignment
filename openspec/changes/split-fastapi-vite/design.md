## Context

Today one Next.js 16 app serves everything on one origin:
- the JSON API: route handlers wrapped by `handle()`, with Zod contracts
- the web UI: Server Components, Server Actions, and an `HttpOnly` cookie holding the session token
- `/docs` (Scalar)

Better Auth owns password hashing (scrypt) and sessions, and Drizzle owns the schema and migrations. Production runs on Vercel with Neon Postgres; locally, Postgres runs in Docker. `scripts/api-smoke.sh` is a curl and psql test of every endpoint and security rule (102 checks), and it doesn't care what language the server is written in.

The user decided:
- FastAPI, code-first
- Vite + React
- the token in `localStorage` as a bearer header
- `backend/` and `frontend/` in one repo
- wipe production data

The API's paths, shapes, status codes and error format stay as they are, so the smoke test can prove the rewrite behaves the same.

## Goals / Non-Goals

**Goals:**
- Two independently runnable apps on separate origins, with CORS configured deliberately.
- Authentication written in the project, where every security decision is visible: hashing, token generation and storage, expiry and revocation.
- One contract: FastAPI's OpenAPI document, generated from Pydantic, committed, and turned into the frontend's types. CI catches drift at both ends.
- The same API behavior as today, proven by the existing smoke test.
- A fresh clone runs with `./scripts/start.sh`.

**Non-Goals:**
- New product features, login rate limiting, email verification or password reset (unchanged from today).
- Refresh tokens or JWTs.
- Server-side rendering of the frontend.
- Keeping existing user data (the user chose to wipe it).

## Decisions

### Repository layout
```
backend/            FastAPI app (uv project)
  app/
    main.py         app factory: routers, CORS, exception handlers, OpenAPI settings
    config.py       pydantic-settings (DATABASE_URL, CORS_ORIGINS, SESSION_TTL_DAYS)
    db.py           engine, session factory, get_db dependency
    models.py       SQLAlchemy models: User, UserPassword, Session
    schemas.py      Pydantic DTOs (requests, responses, ErrorResponse, ErrorCode)
    security.py     argon2id hashing, token generation and hashing
    deps.py         current_session dependency (bearer → session or 401)
    services/       account rules (register, login, change email/password, update, delete)
    routers/        health.py, auth.py, users.py
    errors.py       ApiError, exception handlers
    openapi.py      `python -m app.openapi [--check]`
    seed.py         `python -m app.seed`
  alembic/          migrations
  pyproject.toml, uv.lock, .env.example
frontend/           Vite + React SPA
  src/api/          generated by @hey-api/openapi-ts (committed)
  src/components/   ui/ (shadcn), account/, auth/, layout/ (ported from today)
  src/lib/          auth context, API client setup, safeNext, form helpers
  src/routes/       login, register, home, account, route guard
  index.html, vite.config.ts, openapi-ts.config.ts, package.json, .env.example
openapi/openapi.json  the contract (written by the backend, read by the frontend)
docker-compose.yml, scripts/, .github/workflows/ci.yml, README.md
```
The root `package.json`, `src/`, Next and Drizzle config and `drizzle/` are removed. The spec file stays at the repository root rather than in either app, because both apps depend on it.

### Sync SQLAlchemy with psycopg 3, not async
FastAPI runs plain `def` endpoints in a thread pool, so sync SQLAlchemy is simple and fast enough for this load. Async (asyncpg) would add `await` everywhere and some session-handling complexity for no measurable gain here. Neon's pooled endpoint runs PgBouncer in transaction mode, so we set `prepare_threshold=None` on the psycopg connection to avoid prepared statements (the same concern as today's `prepare: false`). Alternative considered: SQLModel. We rejected it to keep the ORM models and the API DTOs as separate classes, so a database column can never become an API field by accident.

### Hashing: argon2id via pwdlib
`pwdlib[argon2]` is what FastAPI's security docs now use. It wraps `argon2-cffi`, whose defaults (m=64 MiB, t=3, p=4) are above OWASP's argon2id minimums. `PasswordHash.verify_and_update` also lets us rehash later if parameters change. For an unknown user, login runs `verify` against a module-level dummy hash so that path takes as long as a wrong password. Alternatives: bcrypt, which truncates at 72 bytes and is weaker against GPUs; scrypt, today's choice through Better Auth, which is fine, but argon2id is OWASP's first choice.

### Opaque session tokens, stored hashed
`secrets.token_urlsafe(32)` gives 256 bits. The database stores `sha256(token)` in `sessions.token_hash` (unique), so a leaked database can't be used to log in. A fast hash is appropriate here because the input is random, not a password. Lookup is by `token_hash`, followed by an `expires_at > now()` check.
- **Sliding expiry:** `expires_at` moves forward when it was last extended more than a day ago, which limits writes to at most one per session per day. This mirrors Better Auth's `updateAge`.
- **Revocation:** logout deletes one row; a password change deletes all of the user's rows and creates one new session; `ON DELETE CASCADE` handles account deletion.

Alternative: JWTs. We rejected them because revocation would need a denylist, which puts a database lookup back into every request and takes away JWT's one advantage.

### Error handling
One `ApiError(status, code, message)` exception, plus handlers for:
- `ApiError` → our error shape
- `RequestValidationError` → `400 VALIDATION_ERROR`, with `details` built only from `loc` (minus the leading `body`/`path`), `type` and `msg`. Pydantic's `input` is dropped so passwords are never echoed.
- Starlette `HTTPException` (404, 405) → our shape
- `Exception` → logged, then `500 INTERNAL`

Route-level `responses={...}` declare the error model for each status, so the OpenAPI document keeps documenting every status as it does today.

### DTOs and OpenAPI shape
- **Field names:** a shared Pydantic base with `alias_generator=to_camel` and `populate_by_name=True`, with responses serialized by alias. Request models default to `extra="ignore"`.
- **Stable names:** `operationId`s are set explicitly (`register`, `login`, `getCurrentUser`, …) and component names match today's (`User`, `ErrorCode`, `Error`, `LoginBody`, …). The generated frontend functions get stable names, and the smoke test's OpenAPI checks keep working.
- **Security scheme:** `HTTPBearer(scheme_name="bearerAuth", auto_error=False)`, so a missing token becomes our `401` rather than FastAPI's `403`.
- **URLs:** `openapi_url="/api/openapi.json"` and `docs_url="/docs"` (Swagger UI).
- **Login aliases:** `LoginBody` has optional `identifier`/`email`/`username` plus a `model_validator` that picks the first one given, the same behavior as today's Zod transform.
- **Emails:** stored lowercased, with a plain unique index. Registration checks for taken emails and usernames first, to report `EMAIL_TAKEN` before `USERNAME_TAKEN`. It then relies on the unique constraints, catching `IntegrityError` by constraint name for the rare case where two registrations race.

### The frontend's API client: hey-api
`@hey-api/openapi-ts` with the `@hey-api/client-fetch` client and the `@tanstack/react-query` plugin generates into `src/api/` from `../openapi/openapi.json`.
- **Client setup:** at startup, `client.setConfig({ baseUrl: import.meta.env.VITE_API_URL, auth: () => localStorage.token })`. The generated client calls `auth` only for operations that declare `bearerAuth`, so the token goes out as `Authorization: Bearer <token>` on protected endpoints and never to register or login. (Implemented this way instead of a request interceptor, which would add the header to every request.)
- **401 handling:** a response interceptor clears the token on `401` and tells the auth context to go to login. An exception is the password-confirming endpoints, which return `403` for a wrong password, so they never trigger it.
- **`api:check`:** regenerates into a temp dir and diffs against `src/api/`.

Alternatives: openapi-typescript + openapi-fetch (types only, fine but hand-written calls); OpenAPI Generator `typescript-fetch` (classes, but a Java toolchain and verbose output).

### Frontend state and routing
- **Server state:** TanStack Query. `GET /api/auth/me` is the `currentUser` query, invalidated after profile or email changes.
- **Auth context:** exposes `user`, `signIn(token)` and `signOut()`.
- **Routing:** React Router with a `RequireAuth` layout route for `/` and `/account`, and a `PublicOnly` route for `/login` and `/register`.
- **Forms:** keep today's shadcn markup and use plain component state, no form library. API `VALIDATION_ERROR` details are mapped to fields by path, as `lib/forms.ts` does today.
- **Ported code:** `safeNext` is ported unchanged, and the shadcn `ui/` components are copied as they are.

### Content-Security-Policy
A small Vite plugin (`apply: "build"`) injects `<meta http-equiv="Content-Security-Policy">`:
```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' <VITE_API_URL>; object-src 'none'; base-uri 'self'; form-action 'self'
```
- **Fonts:** bundled through `@fontsource`, so the policy needs no Google Fonts host.
- **Inline styles (verified in implementation):** `style-src` is `'self' 'unsafe-inline'`. Radix's scroll lock (`react-remove-scroll`, used by the dialog and the dropdown menu) and Sonner insert `<style>` elements at runtime, and the scroll lock's content is computed per use, so no hash can allow it. A static site can't hand out per-response nonces either. Inline styles are a much smaller risk than inline scripts, and `script-src` stays `'self'`, which is what protects the token.
- **Framing:** `frame-ancestors 'none'` comes from the hosting config header (`vercel.json`), since meta policies ignore it.

### CORS
Starlette's `CORSMiddleware` with `allow_origins=settings.cors_origins`, `allow_methods=["GET","POST","PATCH","DELETE"]`, `allow_headers=["Authorization","Content-Type"]` and `allow_credentials=False`, added as the outermost middleware so error responses carry the headers too. Local default: `http://localhost:5173`. No wildcard, even though no credentials are involved, so the allow-list stays meaningful.

### Scripts and CI
- **Scripts:** `scripts/` keeps `db-up.sh`/`db-down.sh`. `db-migrate.sh` and `db-seed.sh` call `uv run`. New `dev-backend.sh` and `dev-frontend.sh`. `start.sh` runs the setup chain, then starts both servers with a `trap` that kills both on exit.
- **Smoke test:** base URL `http://localhost:8000`. Its SQL helper uses `psql "$DATABASE_URL"` when `psql` is installed and falls back to `docker compose exec db psql`. The hash scan reads `user_passwords.hash` and `sessions.token_hash`, and the expired-session check updates `sessions.expires_at` by `token_hash`, computed with `shasum -a 256`.
- **CI, backend job:** a Postgres 17 service, `uv sync`, `ruff check` and `ruff format --check`, `alembic upgrade head`, `python -m app.openapi --check`, then start uvicorn and run `api-smoke.sh`.
- **CI, frontend job:** `npm ci`, `api:check`, typecheck, lint, build.

### Hosting
The frontend stays on Vercel: the existing project, re-pointed at `frontend/` as a Vite static site with an SPA rewrite and the `frame-ancestors` header. For the backend, see Open Questions. Whichever host, migrations run as a deploy step (`alembic upgrade head`) against Neon's direct, unpooled URL.

## Risks / Trade-offs

- **[XSS can read a token in `localStorage`]** → Mitigations: React escaping, no `dangerouslySetInnerHTML` (checked by lint), and the strict CSP above. Tokens can also be revoked on the server. We accept this knowingly in exchange for simple cross-origin auth, and it's worth explaining in the journal.
- **[A rewrite changes subtle behavior]** → The smoke test runs unchanged apart from its base URL and table names. Its OpenAPI checks pin the operation names and security declarations, and it runs in CI on every PR.
- **[Neon and serverless connection limits]** → A small pool (`pool_size=5`), `pool_pre_ping=True`, and the pooled URL at runtime; migrations use the direct URL.
- **[CSP breaks Radix or Tailwind at runtime]** → Verify the production build in a browser (`vite preview`). Relax only `style-src` if needed.
- **[The first migration drops tables]** → This is intentional (the user chose to wipe). It only drops the known old tables, and only if they exist. It's a one-way migration: a rollback means redeploying the old commit and restoring from a Neon branch snapshot (see Migration Plan).
- **[Two apps, three env files]** → `start.sh` creates all of them from their examples, and the README lists each variable.

## Migration Plan

1. Build everything on `feat/fastapi-vite-split`. Locally, run `./scripts/db-down.sh --reset` once, or let the first Alembic migration drop the old tables.
2. CI green: backend smoke test, frontend build and client check.
3. Before merging, create a Neon branch as a snapshot of `production`, for rollback.
4. Configure hosting: the backend project/service (see Open Questions) with `DATABASE_URL`, `DATABASE_URL_UNPOOLED` and `CORS_ORIGINS=<frontend URL>`; the frontend project with root `frontend/`, framework Vite, and `VITE_API_URL=<backend URL>`.
5. Merge. The backend deploy runs `alembic upgrade head` (dropping the old tables, creating the new ones), then the frontend deploys. Seed `NYUgrader` in production only if the user wants it.
6. Rollback: redeploy the previous `master` commit on the old single-project setup, and restore the database from the snapshot branch.

## Open Questions

- **Where does the backend run in production?** *Decided: Vercel,* as a second project with root `backend/`, next to the frontend project. The two stay on separate origins (for example `<app>.vercel.app` and `<api>.vercel.app`), so the CORS allow-list is used in production exactly as it is locally. A same-origin setup (Vercel Services, or a rewrite of `/api/*` from the frontend project) was considered and rejected: it would hide the cross-origin behavior this change exists to make visible, and production would differ from local development. FastAPI is detected from `app/main.py` with no configuration and runs as one function on Fluid Compute, so the connection pool (`pool_size=5`) is per instance, over Neon's pooled URL.
- **Should `NYUgrader` also exist in production?** Default: no; it's seeded locally only.
